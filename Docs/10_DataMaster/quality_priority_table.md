# 品質観点優先順位表

## 1. 目的

この文書は、Mirror Principle の Z軸候補から、対象に適用する品質観点をAIが選択する際の共通優先順位および判断基準を定義する。  
この品質観点優先順位表は、特定のアプリケーション層、テストフレームワーク、プログラミング言語、UI、API、Backend、Database等に依存しない。  
対象値が、
- どのような型であるか
- どのような意味を持つか
- どのように入力されるか
- どのように変換されるか
- どのように利用されるか
- どこへ保存されるか
- どこへ渡されるか
- どのように表示されるか
- どのような処理系に解釈されるか
等の文脈をもとに品質観点を判断する。  

## 2. 基本原則

品質観点は、単に候補に存在するという理由だけですべて選択してはいけない。  
一方で、明示的な業務意味、annotation、validation等が不足しているという理由だけで、Z軸を `-` としてはいけない。  
品質観点の判断では、次の順序を基本とする。  
1. 明示的なannotation、validation、enum、型情報
2. targetName、fieldName、argName、DTO名等の名称情報
3. className、methodName、周辺引数、return等の処理文脈
4. 入力、変換、保存、表示、出力、実行、外部連携等の利用文脈
5. 本品質観点優先順位表
1～4から明確な業務意味を判断できない場合でも、5の品質観点優先順位表を使用し、対象の型・名称・文脈と明確に矛盾しない一般品質観点を評価する。  
ただし、特定の解釈系または実行系への到達を前提とする品質観点については、単に対象と矛盾しないことだけを選択根拠としてはいけない。  

## 3. プロジェクト品質要求水準との関係

品質観点の選択では、プロンプト側で人が指定したプロジェクト品質要求水準を必ず考慮する。  
品質要求水準そのものを、対象の名称、業界、class、method、annotation、その他の情報からAIが再評価または変更してはいけない。  
AIは指定された品質要求水準を正として扱う。  
品質要求水準は、Mirror候補の意味を書き換えるものではない。  
また、品質要求水準ごとに機械的なケース数を決定するものでもない。  指定された品質要求水準が高いほど、適用可能性のある品質観点について取りこぼしを避ける方向で評価する。  
指定された品質要求水準が低い場合は、対象との関連性、発生可能性、代表性等をより重視して選択する。  
ただし、明示的な制約、必須境界、enum、対象の意味に直接対応する品質観点等を、単に品質要求水準が低いという理由だけで除外してはいけない。  

## 4. 選択の基本方針

Z軸候補は、zCandidateIds および zCandidateDetails に存在する候補の中からのみ選択する。  
候補に存在しないZ軸をAIが新規作成してはいけない。  
候補に存在する場合でも、対象と明確に矛盾する品質観点は選択しない。  
対象と矛盾しないという理由だけで、すべての候補を選択してはいけない。  
対象に対して品質上確認する合理的な価値があるかを判断する。  
判断時には、指定されたプロジェクト品質要求水準も考慮する。  

## 5. 一般品質観点と業務固有品質観点

品質観点は大きく、
- 一般品質観点
- 特定解釈経路を必要とする品質観点
- 業務固有品質観点
に分けて考える。  
一般品質観点は、明確な業務意味が取得できない場合でも比較的積極的に評価する。  
例：
- NULL
- Empty
- 空白
- tab
- 改行
- 制御文字
- Unicode
- surrogate pair
- 環境依存文字
- マッピング差異文字
- 全角・半角混在
- 数値表現差異
- 日付時刻特殊値

特定解釈経路を必要とする品質観点は、対象値そのものが特定の構文または実行系として解釈される合理的な根拠がある場合にのみ選択する。  
例：
- SQL Injection
- HTML / Script Injection
- OS Command Injection
- 数式・Expression等の特殊解釈

業務固有品質観点は、対象の意味を示す合理的な根拠がある場合に選択する。  
例：

- email
- 電話番号
- 郵便番号
- 特定業務コード
- 特定識別番号
- 独自format

対象名称や処理文脈に根拠がない状態で、業務固有形式を推測してはいけない。  

## 6. 品質観点優先順位

| 優先度 | 品質観点 | 基本判断 |
| --- | --- | --- |
| 1 | NULL・未設定・Empty系 | nullable、optional、未設定状態、空値を確認する価値がある場合に優先する |
| 2 | 空白・不可視文字系 | STRING等の文字入力について積極的に評価する |
| 3 | 改行・制御文字系 | 文字列の保存、比較、変換、表示等に影響する可能性を評価する |
| 4 | Unicode・文字コード系 | Unicode、surrogate、環境依存文字、mapping差異等を積極的に評価する |
| 5 | 全角・半角・文字種混在系 | 文字種差異を許容または処理する対象で積極的に評価する |
| 6 | Enum・定義値妥当性系 | enumまたは定義済みコード集合が存在する場合に優先する |
| 7 | 日付・時刻特殊系 | DATE、DATETIME、日時を意味するtargetで優先する |
| 8 | 数値表現差異系 | NUMBER、DECIMAL等の数値targetで優先する |
| 9 | 記号・複合文字列系 | 記号、文字種混在、区切り文字等による処理差を評価する |
| 10 | 一般フォーマット系 | 明示的なformatや構造が確認できる場合に評価する |
| 11 | SQL Injection系 | 対象値そのものがSQLとして解釈される経路への到達に合理的根拠がある場合に限定する |
| 12 | HTML・Script Injection系 | 対象値そのものがHTMLまたはScriptとして解釈される経路への到達に合理的根拠がある場合に限定する |
| 13 | OS・Command Injection系 | 対象値そのものがOS command、shell、process実行へ渡される合理的根拠がある場合に限定する |
| 14 | 数式・特殊解釈系 | 対象値そのものが数式、expression、formula等として解釈される場合に評価する |
| 15 | 業務固有形式系 | email、電話番号、郵便番号等、意味を示す明確な根拠がある場合のみ評価する |


## 7. NULL・未設定・Empty系

NULL、未設定、Empty、Undefined等は、対象が取り得る状態と矛盾しない場合に優先して評価する。  
nullable情報が明示されている場合は、その情報を優先する。  
nullableが不明であることだけを理由に、NULL系品質観点を自動的に除外してはいけない。  
ただし、型または構造上明確に成立しない状態を無理に適用してはいけない。  
Y軸のNULL・Empty境界ケースと意味的に同一のケースをZ軸で重複生成しないよう注意する。  
Z軸として選択する場合は、単なる長さ境界ではなく、NULL、DB_NULL、Undefined等の意味的に異なる状態であることを確認する。  

## 8. 空白・不可視文字系

文字列targetについては、空白および不可視文字を一般品質観点として積極的に評価する。  
候補例：
- space
- tab
- line break
- CRLF
- LF
- その他不可視文字

明確な業務意味が存在しない場合でも、文字列の比較、保存、trim、変換、表示等に影響する可能性があるため、候補と対象が矛盾しなければ評価する。  
指定された品質要求水準が高い場合は、一般的な文字列targetについても取りこぼしを避ける方向で評価する。  

## 9. 改行・制御文字系

制御文字は、文字列の保存、出力、通信、比較、serialization、ログ、表示等へ影響する可能性がある。  
候補に存在し、対象が文字列として扱われる場合は積極的に評価する。  
ただし、同じ意味の候補を重複して選択してはいけない。  

## 10. Unicode・文字コード系

Unicodeおよび文字コード関連の品質観点は、文字列targetに対する一般品質観点として積極的に評価する。  
候補例：
- surrogate_pair
- environment-dependent_character
- character_with_mapping_differences

対象について明示的な業務意味が不足している場合でも、文字列として保存、変換、比較、表示、送受信される可能性があるなら評価対象としてよい。  
単にASCIIのみであると推測してUnicode系品質観点を除外してはいけない。  
指定された品質要求水準が高い場合は、Unicodeおよび文字コード差異による取りこぼしを避ける方向で評価する。  

## 11. 全角・半角・文字種混在系

全角、半角、英字、数字、記号、かな、その他文字種の混在は、文字列品質として一般的に評価する。  
candidateに存在し、対象の型・意味と矛盾しない場合は、明示的なformat情報がなくても評価してよい。  
特に、
- 全角と半角の混在
- 数字と文字の混在
- 記号を含む文字列
等は、正規化、比較、検索、変換処理等への影響を考慮する。  

## 12. Enum・定義値妥当性系

enum、コード値一覧、定義済み選択肢等が確認できる場合は、定義内および定義外を優先して評価する。  
候補例：
- within_definition
- outside_the_definition

enum情報が明示されているにもかかわらず、一般文字列観点だけを生成して定義値妥当性を省略してはいけない。  
これは対象の意味そのものに近い品質観点であるため、プロジェクト品質要求水準が低い場合でも安易に除外してはいけない。  

## 13. 日付・時刻特殊系

DATE、DATETIME、TIME、日時関連名称等から日時を扱う対象と判断できる場合は、日時固有のZ軸を優先する。  
候補に存在する範囲で、
- 日付境界
- 時刻境界
- timezone
- leap year
- 存在しない日時
- 特殊日時表現
等を評価する。  
日時である根拠がない文字列へ日時固有観点を適用してはいけない。  

## 14. 数値表現差異系

NUMBER、DECIMAL、または数値を意味するtargetについては、数値固有の表現差異を評価する。  
候補例：
- positive
- zero
- negative
- decimal
- integer representation
- その他数値特殊表現

Y軸の桁数・境界値テストとは役割を分ける。  
Y軸は、長さ、桁数、件数、min、max等の境界を扱う。  
Z軸は、数値としての意味的・表現的分類を扱う。  

## 15. 記号・複合文字列系

STRING等について、記号、区切り文字、複数文字種の混在が処理へ影響する可能性を評価する。  
ただし、対象の意味が明確でない状態で特定の業務formatまで推測してはいけない。  
一般的な記号・混在文字列と、業務固有formatは区別する。  

## 16. 一般フォーマット系

annotation、validation、targetName、DTO名、methodName、周辺文脈等から明示的なformatが確認できる場合は、そのformatに対応するZ軸を評価する。  
formatに関する根拠が存在しない場合は、AIが新しいformatを推測してはいけない。  
一般文字列品質観点へフォールバックする。  

## 17. Injection系共通原則

Injection系Zは、一般的な文字列品質観点とは明確に分離して扱う。  
対象がSTRINGであること、外部から値を受け取ること、Databaseを利用するapplicationであること、Web applicationであること等だけを理由に、Injection系Zを選択してはいけない。  
また、指定されたプロジェクト品質要求水準が高いことだけを理由に、Injection系Zを追加してはいけない。  
Injection系品質観点は、対象値そのものが特定の構文または実行系へ到達し、その構文または実行系として解釈されると判断できる合理的な根拠がある場合に選択する。  
判断には、
- targetName
- fieldName
- argName
- className
- methodName
- annotation
- 周辺引数
- return情報
- method context
- 入力用途
- 変換先
- 出力先
- 外部連携先

等を使用する。  
対象がどのアプリケーション層に存在するかだけを理由に適用可否を判断してはいけない。  
また、「最終的にどこかの画面に表示されるかもしれない」「どこかでSQLに利用されるかもしれない」「外部入力なのでcommandへ渡るかもしれない」等の可能性だけを、解釈経路の根拠としてはいけない。  

## 18. SQL Injection系

SQL Injection系は、対象値そのものがSQL構文またはSQL評価対象として解釈される処理へ到達すると判断できる場合に選択する。  
選択根拠の例：
- SQL文字列そのものの生成
- 動的query生成
- SQL構文要素としての利用
- table名、column名等をSQL構文へ動的に組み込む処理
- query条件をSQL文字列として直接構築する処理
- SQL評価へ到達することを示すmethod文脈

単に、
- Database接続情報である
- Repository classに存在する
- JDBCを利用している
- STRING型である
- applicationがDatabaseを利用している
- DBへ保存される値である
という理由だけでは選択しない。  
値がparameter binding等によって単なるデータとして扱われることが明確な場合は、SQL Injection品質観点の優先度を下げる。  
SQLに関係する名称であることと、対象値そのものがSQLとして解釈されることを混同してはいけない。  

## 19. HTML・Script Injection系

HTML・Script Injection系は、対象値そのものがHTML、markup、DOMへ挿入されるHTML断片、Script、その他browser等によって構文または実行可能内容として解釈される経路へ到達すると判断できる場合に選択する。  
選択根拠の例：
- HTML文字列そのものの生成
- raw HTMLとしての埋込み
- markup生成
- HTML templateへの非エスケープ挿入
- script生成
- script内容としての利用
- DOMへHTMLとして挿入する処理
- browser等がmarkupまたはscriptとして解釈する形式への出力

一方、以下だけでは選択根拠として不十分である。  
- STRING型である
- Web application内で使用される
- HTTPで送受信される
- DBへ保存される
- 通常の文字列として画面表示される可能性がある
- `template` という名称を含む
- title、name、host、username、password、schemaName、tableName等の一般文字列である
通常の文字列表示と、HTMLまたはScriptとしての解釈は明確に区別する。  
文字列が最終的に画面へ表示され得るというだけでは、HTML・Script Injection系Zを選択してはいけない。  
対象値そのものがHTMLまたはScriptとして解釈されることを示す合理的な文脈が必要である。  

## 20. OS・Command Injection系

OS・Command Injection系は、対象値そのものがOS command、shell command、process実行引数または実行可能なcommand文字列として解釈されると判断できる場合にのみ選択する。  
選択根拠の例：
- command文字列生成
- shell実行
- process起動
- executable argumentとしての利用
- OS commandとして評価される文字列生成

単に、
- STRING型である
- filepathである
- 外部入力である
- server側処理である
- OS上で動作するapplicationである
という理由だけでは選択しない。  
Injection系の中でも、OS・Command Injectionは特に適用条件を厳しくする。  

## 21. 数式・特殊解釈系

対象値そのものが、
- 数式
- expression
- formula
- query expression
- spreadsheet式
- その他評価可能な構文
として解釈される場合、数式・特殊解釈系Zを評価する。  
通常のNUMBERやSTRINGであることだけを理由に、数式観点を選択してはいけない。  
対象値が式として評価される合理的な文脈が必要である。  
単に数値を格納する、表示する、計算結果を保持するというだけでは、数式として解釈されることを意味しない。  

## 22. 業務固有形式系

業務固有形式は、一般品質観点よりも慎重に選択する。  
候補例：
- email
- phone
- postal
- 特定業務コード
- 特定識別子
- 独自固定format

次のような明確な意味情報がある場合に選択する。  
- targetName
- fieldName
- argName
- DTO名
- annotation
- validation
- methodName
- className
- 周辺文脈

例えば、emailAddress、mailAddress、postalCode、phoneNumber等の意味が明確であれば、対応するZ軸を評価してよい。  
一方、name、value、text、data等の一般名称だけからemail、電話番号、郵便番号等を推測してはいけない。  
指定されたプロジェクト品質要求水準が高い場合でも、業務意味そのものをAIが発明してはいけない。  

## 23. 情報不足時のフォールバック

対象の業務意味を十分に判断できない場合は、次の順序で判断する。  
明示的意味情報あり → 対応するZ軸を優先する。  
明示的意味情報なし → 本品質観点優先順位表へフォールバックする。  
品質観点表から、対象の型・名称・文脈と明確に矛盾しない一般品質観点を評価する。  
その際、指定されたプロジェクト品質要求水準を考慮し、必要な品質観点の取りこぼしを避ける。  
ただし、Injection、特殊解釈、業務固有形式等については、情報不足を一般品質観点として補完してはいけない。  
これらは、それぞれに必要な解釈経路または業務意味を示す合理的な根拠が存在する場合のみ選択する。  
一般品質観点にも適用根拠がない場合 → Zを `-` とする。  
したがって、情報不足=即座にZを `-`するのではない。  
一方で、情報不足=すべてのZ候補を採用するものでもない。  

## 24. Z軸を `-` とする条件

次の場合はZを `-` としてよい。  
- zCandidateIdsに利用可能な候補が存在しない
- candidateと対象の型が明確に矛盾する
- candidateと対象の意味が明確に矛盾する
- candidateの成立に必要な処理文脈が存在しない
- candidateの成立に必要な解釈経路を示す根拠が存在しない
- 品質観点として確認する合理的価値がない
- 他のXまたはYケースと完全に同義であり重複になる

ただし、業務意味が不明であることだけを理由にZを `-` としてはいけない。  
一般品質観点へフォールバックできるかを先に確認する。  

## 25. 過剰選択の禁止

品質観点優先順位表は、すべての品質観点をすべてのtargetへ適用するための表ではない。  
例えば、STRINGであるという理由だけで、
- SQL Injection
- OS Command Injection
- HTML/Script Injection
- email
- phone
- postal
をすべて選択してはいけない。  
また、プロジェクト品質要求水準が高いという理由だけで、特定解釈経路を必要とする品質観点や業務固有品質観点まで無条件に追加してはいけない。  
同様に、candidateに存在するという理由だけで全Z候補を採用してはいけない。  
品質上の価値、対象文脈、必要な意味情報、必要な解釈経路を確認して選択する。  

## 26. 過少選択の禁止

一方で、annotation、validation、業務名称等が不足していることを理由に、一般品質観点をすべて除外してはいけない。  
特に文字列targetについて、
- 空白
- tab
- 改行
- 制御文字
- Unicode
- surrogate pair
- 環境依存文字
- mapping差異
- 全角・半角混在

等は、candidateに存在し、対象と明確に矛盾しない場合、積極的に評価する。  
指定されたプロジェクト品質要求水準が高い場合は、これら一般品質観点について取りこぼしを避ける方向で評価する。  
ただし、Injection等をこの一般品質観点の積極選択ルールへ含めてはいけない。  

## 27. Mirror候補優先

最終的なZ軸選択では、必ず入力されたMirror候補を正とする。  
品質観点優先順位表は、新しいMirror IDを生成するための資料ではない。  
この表は、「候補として既に存在するZのうち、どれを選択する価値があるか」を判断するために使用する。  
Mirror Zの正式なID、名称、階層、意味については、入力されたMirror Zデータを優先する。  

## 28. 最終判断原則

Z軸選択は、次の原則で行う。  
明確な意味がある → その意味に対応するZを優先する。  
意味情報が不足する → 一般品質観点へフォールバックする。  
一般品質観点が対象と矛盾しない → 指定された品質要求水準も考慮し、品質上価値があるものを積極的に選択する。  
Injection等、特定の解釈経路が必要な品質観点 → 対象値そのものがその構文または実行系として解釈される経路を示す合理的な根拠がある場合のみ選択する。  
業務固有形式 → 業務意味を示す合理的な根拠がある場合のみ選択する。  
どの品質観点にも適用根拠がない → Zを `-` とする。  
Z軸は、多ければよいわけでも、少なければよいわけでもない。  
対象について、指定された品質要求水準に応じて必要な品質観点を十分に網羅することが適切である。
