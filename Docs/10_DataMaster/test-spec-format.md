# テスト仕様書フォーマット-鏡の原理自動化版

## 用途

- 以下に示す内容をテーブル化して利用し、別途規定するテスト用途毎に「適宜」必要であれば最適化するためのフォーマットとする。
- このファイルでは便宜上リストおよびMarkdownテーブルで示すが、基本的なフォーマットはテーブル形式とし、ExcelないしCSVとして流用可能なものとする。
- テストケースはテスト仕様書の1レコードとして扱う。
- 鏡の原理を利用するテストでは、観点IDをX軸・Y軸・Z軸に分離する。
- テスト仕様書は人間が読む仕様書であると同時に、テストデータGeneratorおよびテストコード生成時の契約データとして利用可能な形式とする。

## テスト仕様書フォーマット

- CaseNo
- targetId
- 大分類
- 中分類
- 小分類
- 観点ID_X
- 観点ID_Y
- 観点ID_Z
- ケース内容
- 操作手順
- 確認内容
- 確認手順
- 想定結果
- 想定結果判断基準・判断手順
- generatorTarget
- generatorRule
- テスト実施記録（個人開発ならば不要としても可）
  - 予定日
  - 実施日
  - 実施者
  - 実施結果
- テスト再実施（個人開発ならば不要としても可）
  - 再実施要否
  - 再実施判断日
  - 再実施判断担当者
  - 再実施テスト仕様書ファイル名ないしファイルパス
- 備考

## テスト仕様書フォーマット解説

### CaseNo

- テストケースを一意に識別するケースナンバーとする。
- 8、16、24、32といったいずれかの桁で構成する数字とIDを紐付けたものとする。
- IPアドレスと同様に、各桁ないし各区分へ意味を持たせる考え方を採用できる。
- 個人開発の場合でも、ID体系は可能な範囲で全個人開発共通とする。
- システムIDに加えて機能IDやAPIと紐付けられるようにする。
- テスト工程や観点そのものをCaseNoだけで直接表現する必要はない。
- 例：

```text
SYSTEMID-12-34-56-78-910
```

### targetId

- AST、Cleaner、SQLite VIEWによって生成されたテスト対象の一意識別子。
- `v_ai_input.targetId` をそのまま使用する。
- AIはtargetIdを変更、新規生成、要約してはならない。
- テスト仕様書、Data Generator、テストデータ、テストコードを接続する契約キーとして利用する。
- generatorTargetと同値でなければならない。

### 大分類

- 単体画面、単体API、結合画面、結合APIなど、テストの大きな粒度を記載する。

### 中分類

- 利用するシーンやプロジェクトに応じて定義する。
- 固定値とはせず、テスト対象に適した分類を使用する。

### 小分類

- 利用するシーンやプロジェクトに応じて定義する。
- テストケースの目的を識別しやすい粒度で記載する。

### 観点ID_X

- 鏡の原理X軸にリンクする観点ID。
- X軸を使用しないケースでは `-` とする。
- AIは `v_ai_input.xCandidateIds` に存在する候補以外を生成してはならない。
- 具体的なテスト値は記載しない。

### 観点ID_Y

- 鏡の原理Y軸にリンクする観点ID。
- Y軸を使用しないケースでは `-` とする。
- AIは `v_ai_input.yCandidateIds` に存在する候補以外を生成してはならない。
- min、max、length、digit、quantity等に関する具体値はData Generatorが後から生成する。

### 観点ID_Z

- 鏡の原理Z軸にリンクする観点ID。
- Z軸を使用しないケースでは `-` とする。
- AIは `v_ai_input.zCandidateIds` に存在する候補以外を生成してはならない。
- method名、field名、DTO名、annotation、methodSemanticContext等の意味情報から選択する。
- 判断できない場合に推測で選択してはならない。

### ケース内容

- 何をテストするケースであるかを自然言語で記載する。
- Mirror IDそのものの単純な言い換えではなく、対象と観点を結び付けて記載する。
- Data Generatorが生成する具体的な入力値そのものは記載しない。

### 操作手順

- テストケースを実施するための操作手順を記載する。
- プログラムを実行するだけの場合は、対象JUnitテスト、コマンド、スクリプトファイル名等を記載してよい。
- 具体的なテストデータ値は原則としてここへ直接固定記載しない。

### 確認内容

- テスト結果として何を確認するかを記載する。
- return値、exception、HTTP status、DTO、DB、ログ等、対象テストに必要な確認対象を明記する。

### 確認手順

- 確認内容を判断するための操作や確認方法を記載する。
- JUnitで自動判定できる場合は、assertion対象や確認方法を自然言語として記載する。

### 想定結果

- テスト実行によって想定される結果を記載する。
- テストコードの場合は、最終的にJUnit assertionへ変換可能な自然言語とする。
- ソース、AST、annotation、Mirror情報等から判断できない内容を推測で断定しない。

### 想定結果判断基準・判断手順

- 想定結果をPASSまたはFAILと判断する基準を記載する。
- 単に結果の繰り返しを書くのではなく、どの状態なら成功・失敗と判断するかを記載する。
- 必要に応じて再実行条件や追加確認条件も記載する。

### generatorTarget

- Data Generatorが値を生成する対象を指定する。
- 必ず `targetId` と同一値とする。

```text
generatorTarget = targetId
```

- AIが独自のgeneratorTargetを作成してはならない。

### generatorRule

- Data Generatorが実行する鏡の原理のルールを機械判定可能な形式で保持する。
- 自然言語を記載してはならない。
- 観点ID_X、観点ID_Y、観点ID_Zから決定される。
- 固定形式を以下とする。

```text
X={観点ID_X}|Y={観点ID_Y}|Z={観点ID_Z}
```

例：

```text
X=-|Y=length_max_plus_1|Z=-
```

または、

```text
X=x_halfwidth_alpha|Y=length_max|Z=-
```

- 使用しない軸は `-` とする。
- generatorRule内のIDと観点ID_X、観点ID_Y、観点ID_Zは必ず一致しなければならない。
- Data Generatorは自然言語のケース内容を解析してルールを決定してはならない。
- generatorRuleのみを機械的な生成命令として使用する。

### テスト実施記録

- 個人開発の場合は省略可能とする。
- プロジェクトの運用に応じて以下を使用する。
  - 予定日
  - 実施日
  - 実施者
  - 実施結果

### テスト再実施

- 個人開発の場合は省略可能とする。
- 必要に応じて以下を使用する。
  - 再実施要否
  - 再実施判断日
  - 再実施判断担当者
  - 再実施テスト仕様書ファイル名ないしファイルパス

### 備考

- 他の列では表現しづらい補足事項を記載する。
- 個人開発の場合でも残してよい。
