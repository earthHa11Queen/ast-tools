# テストケースナンバー採番ルール

## 1. 目的

CaseNoは、テスト仕様書内の各テストケースを一意に識別するためのIDです。
CaseNoはMirror ID、targetId、generatorTargetとは役割が異なります。
- CaseNo
  - 人間およびテスト管理上のテストケース識別子
- targetId
  - ASTおよびSQLiteから生成されたテスト対象識別子
- 観点ID_X / 観点ID_Y / 観点ID_Z
  - 鏡の原理上のテスト観点識別子
- generatorTarget
  - Data Generatorが値を生成する対象
- generatorRule
  - Data Generatorが使用するMirrorルール
したがってCaseNoへtargetIdやMirror IDの全文を埋め込む必要はありません。
CaseNoは、プロジェクトまたは組織で人間が管理しやすい識別体系として使用します。

## 2. 基本方針

CaseNoは原則として8桁から12桁程度の識別子を基本とします。
ただし、プロジェクトまたは会社に既存の採番規則が存在する場合は、その規則を優先してください。
このファイルに記載された規則は、プロジェクトごとに変更して構いません。
フレームワーク全体としてCaseNoの具体的な体系を固定しません。

## 3. 今回使用するCaseNo形式

今回のプロジェクトでは、以下の形式を使用します。

```text
{{CASE_NO_FORMAT}}
```

例：

```text
UTAPI-000001
```

または、

```text
APP01-010001
```

上記は例であり、実際にはこのファイル内で指定された形式を使用してください。

## 4. Prefix

今回使用するCaseNoのprefixは以下です。

```text
{{CASE_NO_PREFIX}}
```

例：

```text
UTAPI
```

prefixが指定されている場合は、AIが独自のprefixを作ってはいけません。
prefixが不要なプロジェクトの場合は、この項目を `NONE` としてください。


## 5. 数値部分の桁数

連番部分は以下の桁数を使用します。

```text
{{CASE_NO_SERIAL_DIGITS}}
```

例：

```text
6
```

6桁の場合、

```text
000001
000002
000003
```

のようにゼロ埋めしてください。


## 6. 区切り文字

prefixと数値部分等を区切る文字は以下です。

```text
{{CASE_NO_SEPARATOR}}
```

例：

```text
-
```

区切り文字が不要な場合は `NONE` としてください。

## 7. 採番開始値

新規CaseNoの採番開始値は以下です。

```text
{{CASE_NO_START}}
```

例：

```text
1
```

既存テスト仕様書にCaseNoが存在する場合は、既存番号との重複を避けてください。

## 8. 既存CaseNoの維持

既存 `v_test_spec` に、

- targetId
- 観点ID_X
- 観点ID_Y
- 観点ID_Z

が一致するケースが存在する場合、
原則として既存CaseNoを維持してください。
自然言語列を修正しただけでCaseNoを変更してはいけません。
これは、同じ論理テストケースがAI再生成のたびに別IDになることを防ぐためです。


## 9. 新規ケースの採番

既存テスト仕様書に対応するケースが存在しない場合のみ、新しいCaseNoを採番してください。
新規採番時は、
1. このファイルで指定されたprefixを確認する
2. このファイルで指定された桁数を確認する
3. 既存CaseNoの最大値を確認する
4. 重複しない次の番号を使用する
5. 指定された形式へ整形する
という順番で処理してください。

## 10. 削除されたケースの番号

ソース変更等によって削除対象となったCaseNoは、原則として再利用しないでください。

例えば、

```text
UTAPI-000010
```

が過去に使用され、そのケースが後に削除された場合でも、新しい別ケースへ `UTAPI-000010` を再割り当てしないでください。
ただし、プロジェクト固有ルールとして再利用を認める場合は、この項目を書き換えてください。

## 11. CaseNoの一意性

最終的なテスト仕様書CSV内で、CaseNoは必ず一意でなければなりません。
同一CaseNoを複数ケースへ割り当ててはいけません。

## 12. CaseNoとケース順序

CaseNoはケース表示順序と完全一致する必要はありません。
既存CaseNoを維持した結果、

```text
000001
000002
000008
000004
```

のような表示順となる場合でも、CaseNoを再採番して並べ直してはいけません。
CaseNoは永続的な識別子であり、単なる行番号ではありません。

## 13. CaseNoとMirror ID

CaseNoからMirror X/Y/Zを推測できる必要はありません。
Mirror観点は、
- 観点ID_X
- 観点ID_Y
- 観点ID_Z
で別途管理されるためです。
したがってCaseNoへMirror IDを機械的に埋め込むことを必須としません。

## 14. CaseNoとtargetId

CaseNoへtargetId全体を埋め込んではいけません。
targetIdはソース構造由来で長く、ソース変更によって変化する可能性があります。
CaseNoは人間向けの比較的安定した識別子として扱います。

## 15. 情報不足時

このファイルの指定だけではCaseNoを確定できない場合、勝手に新しい採番規則を発明してはいけません。
その場合は、可能な範囲で既存CaseNoを維持してください。
新規ケースのCaseNoだけが確定不能な場合は、以下の仮形式を使用できます。

```text
TEMP-000001
```

ただしこれは、プロジェクト固有採番ルールが未設定の場合のみ使用してください。
正式運用では、人間がこのファイルを編集して採番規則を指定することを前提とします。

## 16. 今回の設定値

以下を今回の正式設定として扱ってください。

```yaml
case_no:
  format: "{{CASE_NO_FORMAT}}"
  prefix: "{{CASE_NO_PREFIX}}"
  serial_digits: "{{CASE_NO_SERIAL_DIGITS}}"
  separator: "{{CASE_NO_SEPARATOR}}"
  start: "{{CASE_NO_START}}"
  reuse_deleted_number: false
  preserve_existing_case_no: true
```
