# F200. 生成テスト失敗分類・実施不能マーキングツール 詳細設計書

Version: 0.1.0
対象: ast-tools / mirror-framework パイプライン下流（JUnit実行 → Evidence → Replay）

---

## 1. 目的

生成されたJUnitテストの実行結果から、失敗した各CaseNoを**原因の性質によって分類**し、

- 原理的に実施不能なCaseNoを、**理由を明記した上で実施対象外としてマークする**
- 実施不能と判断した根拠を、**機械可読なカタログとして残す**
- 分類できない失敗を、**握りつぶさず報告する**

ことを目的とする。

本ツールは「テストを通すためのツール」ではない。
**「なぜ通らないのかを確定させ、記録するためのツール」**である。

---

## 2. 設計思想

### 2.1 除外ではなく符号化する

実施不能なCaseNoを削除・コメントアウトすると、

- テスト仕様書のCaseNo総数と、実行されるテスト数の一致が崩れる
- 「見なかった」のか「見られなかった」のかが区別できなくなる

本ツールは削除を行わない。
`@Disabled` によって**実行対象から外しつつ、CaseNoとしては存在させ続ける**。

これは既存のセンチネル値の使い分け

- `-1` : 打ち切り／未判定／該当なし
- `'-'` : 該当なし・空
- `NULL` : 性質として存在し得ない

における `NULL`（性質として存在し得ない）に相当する扱いである。

### 2.2 鏡の原理側を修正しない

「Javaの `int` に `null` を渡せない」「数値に空文字は存在しない」といった事実は、
**言語および型の性質**であって、鏡の原理そのものの欠陥ではない。

したがって本ツールは、AST・SQLite・鏡の原理カタログを一切変更しない。
**実行結果という事実から、実施不能な組み合わせを事後的に確定させる**方式を取る。

カタログを人が机上で列挙すると必ず漏れる。実測から出せば、そのプロジェクト・
その言語・その型について事実として確定する。

### 2.3 エラーが出ること自体に価値がある

原理的にありえない入力でエラーが出るということは、
**実装が余計な加算・減算・暗黙変換を行わず、境界を守っている証拠**である。

エラーを消すことが目的ではない。
**エラーが出るケースを検知し、分類できる状態にすること**が目的である。

## 3. パイプライン上の位置づけ

```
Source
  → AST
  → Cleaner
  → SQLite
  → AIによるTest Specification生成
  → SQLite Validation
  → Validation済みTest Specification
  → SQLiteによるTest Data Instruction生成
  → JUnitコード生成
  → JUnit実行
  → ★ 本ツール（失敗分類・実施不能マーキング）
  → JUnit再実行 / Mutation Testing
  → Evidence
  → Replay
```

JUnit実行の直後、Mutation Testing の直前に位置する。

Mutation Testing（PIT）は失敗テストが存在すると中断するため、
**本ツールを通すことが PIT 実行の前提条件**となる。

---

## 4. 失敗の分類体系

| 分類 | 名称 | 内容 | 処置 |
|---|---|---|---|
| A | TYPE_UNREACHABLE | 言語・型の性質により、その入力条件がSUTに到達し得ない | `@Disabled` |
| A' | GENERATOR_DEFECT | 生成されたテストコード自体の欠陥 | `@Disabled`（暫定） |
| B | ORACLE_ISSUE | オラクルの解釈誤り。修正すればPASSする | **処置しない**（報告のみ） |
| C | SUT_DEFECT | SUTの実装欠陥 | **処置しない**（報告のみ） |
| ? | UNKNOWN | 既知パターンに一致しない | **処置しない**（報告のみ） |

### 4.1 分類BとCを処置しない理由

**分類B** は、オラクルを正しく直せばPASSするテストである。
`@Disabled` にすると、そのCaseNoが本来検証していた契約まで眠らせることになる。
価値あるテストを失うため、処置対象としない。

**分類C** は実バグである。これを `@Disabled` にすることは、
**バグを隠蔽する行為**であり、テスト自動化として最悪の失敗にあたる。

分類BとCはいずれも JUnit の `AssertionFailedError` として現れ、
分類A/A' は `HarnessException` として現れる傾向があるが、
**例外の型だけで判定してはならない**。判定は原因メッセージのパターンで行う。

### 4.2 ホワイトリスト方式

本ツールは **既知の分類A/A'パターンに一致したCaseNoのみ**を処置する。

一致しないものは一切変更せず、未分類として報告する。

この方式により、将来分類Cが発生した場合でも、
**未知パターンとして必ず報告に残り、誤って無効化されることがない**。

## 5. 理由コード体系

| 理由コード | 分類 | 判定パターン（原因メッセージ） | 意味 |
|---|---|---|---|
| `EMPTY_TO_NUMBER` | A | `NumberFormatException: For input string: ""` | 数値型に「長さ0」は存在しない |
| `EMPTY_TO_DATETIME` | A | `DateTimeParseException: Text ''` | 日時型に「長さ0」は存在しない |
| `NULL_TO_PRIMITIVE` | A | `Cannot invoke "java.lang.Number.intValue()"` | プリミティブ型は null を保持できない |
| `INVALID_LITERAL_UNREACHABLE` | A | `DateTimeParseException: Text '__INVALID__'` | 型付きフィールドには不正書式の文字列が入らない |
| `DATE_LITERAL_TO_DATETIME` | A | `DateTimeParseException: Text '<日付のみ>'` | 日付表記を日時型に投入できない |
| `RANGE_UNDEFINED` | A | `out_of_range requires validationMin or validationMax` | 範囲が定義されない型に範囲外値は生成できない |
| `GENERATOR_DEFECT_CONSTRUCTOR` | A' | `Method not found:` かつ対象がコンストラクタ | コンストラクタをメソッドとして呼び出している |
| `ORACLE_ISSUE` | B/C | `org.opentest4j.AssertionFailedError` | オラクル起因またはSUT欠陥。要人間判断 |
| `UNKNOWN` | ? | 上記いずれにも一致しない | 要調査 |

### 5.1 理由コードの意味的な位置づけ

理由コード `A` 系は、いずれも
**「単体テストの観測点では観測できない」**ことを示している。

たとえば `INVALID_LITERAL_UNREACHABLE` は、
「不正な日付文字列を投入したときの振る舞い」を見たいという意図自体は正当だが、
DTOのフィールドが `LocalDateTime` 型である以上、単体レベルでは到達し得ない。

この観点は、**結合APIテスト（JSON → 型へのバインディング）で観測すべき**ものである。

したがって理由コードは「不要なケース」を意味しない。
**「観測点が別工程にあるケース」**を意味する。

## 6. 入出力仕様

### 6.1 入力

| 入力 | パス | 内容 |
|---|---|---|
| テスト実行結果 | `build/test-results/test/*.xml` | JUnit XML。CaseNo・失敗内容・スタックを含む |
| Scenarioソース | `src/test/java/**/unit/scenarios/*.java` | `@Disabled` 挿入対象 |

Scenarioソースの探索は、XML の `classname` 属性から導出する。

### 6.2 出力

#### (1) Scenarioソースへの `@Disabled` 挿入

対象メソッドの直前に、以下を1行挿入する。

```java
    @org.junit.jupiter.api.Disabled("[MIRROR-DISABLED] <理由コード>: <詳細> | dataId=<dataId>")
    void case_UTAPI_010113() {
```

- FQCN で記述するため `import` 追加は不要
- 先頭の `[MIRROR-DISABLED]` は本ツールが付与した目印であり、
  巻き戻し（`--revert`）および冪等性判定に用いる
- 既に同メソッドに目印付きの `@Disabled` がある場合は再挿入しない

#### (2) 実施不能カタログ CSV

`disabled-catalog.csv`

| 列 | 内容 |
|---|---|
| `CaseNo` | ケース番号 |
| `scenarioClass` | Scenarioクラス FQCN |
| `methodName` | JUnitメソッド名 |
| `dataId` | 対象データID（取得できた場合） |
| `category` | TYPE_UNREACHABLE / GENERATOR_DEFECT |
| `reasonCode` | 理由コード |
| `detail` | 原因メッセージ（1行に正規化） |

この CSV が、**そのプロジェクトにおける「型として到達不能な入力条件」の実測カタログ**となる。

将来的には SQLite に取り込み、test_spec と結合して集計する。

#### (3) 未処置レポート CSV

`unhandled-report.csv`

分類 B / C / UNKNOWN として処置しなかった失敗の一覧。
列構成は (2) と同一で、`category` に `ORACLE_ISSUE` / `UNKNOWN` が入る。

**分類C（SUT実バグ）候補はここに現れる。**
本ツール実行後、人間が最初に見るべきファイルはこれである。

#### (4) 標準出力サマリ

```
失敗合計       : N
  @Disabled付与 : N  (理由コード別内訳)
  未処置        : N  (ORACLE_ISSUE / UNKNOWN 別内訳)
変更ファイル数 : N
```

## 7. 動作モード

| モード | オプション | 動作 |
|---|---|---|
| ドライラン | `--dry-run` | ソースを変更せず、CSVとサマリのみ出力 |
| 適用 | (既定) | `@Disabled` を挿入し、CSVとサマリを出力 |
| 巻き戻し | `--revert` | 目印付き `@Disabled` 行をすべて削除 |

### 7.1 冪等性

同一の入力に対して複数回実行しても結果は変わらない。
既に目印付き `@Disabled` が存在するメソッドはスキップする。

### 7.2 巻き戻し可能性

`--revert` により、本ツールが挿入した行のみを削除して原状復帰できる。
目印 `[MIRROR-DISABLED]` を含まない `@Disabled` は削除しない
（人間が別目的で付けたものを壊さないため）。

## 8. 今回の実装範囲

> **本節は、本バージョン（0.1.0）における実装スコープを明示するものである。**
> 設計として想定している全体像は第9章に記す。
> 今回の実装は、その中の最小限の縦断のみを対象とする。

### 8.1 今回の実装で対象とすること

- 対象言語: **Java のみ**
- 対象ビルドツール: **Gradle（JUnit XML 出力形式）のみ**
- 判定方式: **第5章の理由コード表に列挙した既知パターンのみ**
- 判定ロジック: **正規表現によるメッセージ照合**
- 出力: **Scenarioソースへの `@Disabled` 挿入／カタログCSV／未処置レポートCSV**
- 実行契機: **手動実行**

### 8.2 今回の実装で対象としないこと

以下は本バージョンでは実装しない。設計としては第9章のとおり想定している。

- test_data_instruction.csv および test_spec への実施不能フラグの書き戻し
- SQLite への取り込みと集計ビュー
- Java 以外の言語（Python / PHP / Go / TypeScript）への対応
- Maven（Surefire）形式の XML 対応
- 分類B（オラクル起因）の自動修正
- CI への組み込み・自動実行
- 理由コードの外部設定ファイル化

### 8.3 今回の実装における既知の制約

- 理由コードの判定パターンはソース内に定数として保持する
  （将来的には外部CSV化を想定するが、今回はコード内に置く）
- `DATE_LITERAL_TO_DATETIME` の判定は、日付形式の文字列リテラルを
  正規表現で識別する。網羅的ではない
- 1メソッドに複数の失敗が記録される場合は、最初の1件で分類する
- Scenarioソースの整形（インデント・改行）は既存のスタイルを前提とする

## 9. 将来構想

本ツールは、単体で完結するものではなく、
**パイプライン全体の「実施可能性」を管理する層**の入口として設計している。

### 9.1 実施不能情報の上流還元

現在は実行結果からカタログを生成するのみだが、将来的には

```
実行結果
  → 実施不能カタログ
  → test_data_instruction.csv に実施不能フラグを付与
  → test_spec に実施区分（実施可能 / 型制約により実施不能 / 別工程で実施）を付与
  → テスト仕様書上で「なぜ実施しないのか」が読める状態にする
```

という還元を想定する。

これにより、テスト仕様書は
**「網羅した」ではなく「網羅した上で、この範囲は別工程で見る」**と主張できるようになる。

### 9.2 工程間の観測点移動

理由コード `A` 系の多くは、
「単体では観測できないが、結合では観測できる」ケースである。

将来的には、実施不能と判定されたCaseNoを、
**結合APIテストのケース候補として自動的に引き継ぐ**ことを想定する。

- `NULL_TO_PRIMITIVE` → JSON の `null` が API 境界でどう扱われるか
- `INVALID_LITERAL_UNREACHABLE` → 不正書式の日時文字列がバインディングでどう扱われるか
- `EMPTY_TO_NUMBER` → 空文字が数値パラメータとして送られた場合の挙動

これらはいずれも、実務上テストすべき事項である。
**単体で消えるのではなく、結合へ移動する**という扱いが正しい。

### 9.3 言語横断化

理由コードの判定は現在 Java の例外メッセージに依存しているが、
本質的には「型が値を保持できるか」という言語ごとの事実である。

将来的には `lang_data_models.csv` に

- `null_capable`（その型が null を保持できるか）
- `variable_length`（その型に長さ0が定義されるか）

といった列を持たせ、**実行前に判定できる**状態を目指す。

ただしその場合も、本ツールによる**実測との突き合わせ**は残す。
机上の定義と実際の挙動が一致することを確認できる手段は、失ってはならない。

### 9.4 分類の自動精度向上

現在は正規表現によるホワイトリスト方式だが、
実行を重ねることで理由コードの網羅性が上がっていく。

未処置レポートに現れた `UNKNOWN` を人間が分類し、
パターンを追加していくことで、カタログが育つ設計とする。

**未処置レポートが空に近づいていくこと自体が、体系の成熟度を示す指標**となる。

## 10. 使用手順

```bash
# 1. テストを実行して XML を生成する
./gradlew test --console=plain \
  -Dtestdata.runtime.class=... -DtestDataFile=... -DtestDataMode=GENERATE

# 2. まずドライランで分類結果を確認する
python mirror_disable_tool.py --project . --dry-run

# 3. 未処置レポートを確認する（分類C候補の確認）
cat out/unhandled-report.csv

# 4. 問題なければ適用する
python mirror_disable_tool.py --project .

# 5. 再実行して緑になることを確認する
./gradlew test --console=plain --rerun-tasks ...

# 6. 巻き戻す場合
python mirror_disable_tool.py --project . --revert
```

## 11. 判断記録

本設計において、意図的に採用しなかった選択肢を記録する。

| 採用しなかった案 | 理由 |
|---|---|
| ソースのコメントアウトによる除外 | CaseNo総数と実行テスト数の一致が崩れる。レポートに理由が残らない |
| 失敗したテストを一律 `@Disabled` にする | 分類C（実バグ）を隠蔽する危険がある |
| SQLite に除外ビューを追加して事前に生成しない | 言語固有の事実を言語非依存の体系に混入させることになる。また「原理的にありえない入力でエラーが出る」という検知価値を失う |
| 例外の型（HarnessException / AssertionFailedError）だけで分類する | 型と原因は一対一ではない。原因メッセージで判定する必要がある |
| ブラックリスト方式（既知の分類B/C以外を除外） | 未知の失敗が自動的に無効化される。分類Cを取りこぼす |
