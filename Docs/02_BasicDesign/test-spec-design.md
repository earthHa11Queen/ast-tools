
# テスト仕様書フォーマット-基本形

## 用途

- 以下に示す内容をテーブル化して利用し、別途規定するテスト用途毎に｢適宜｣必要であれば最適化するためのフォーマット
- また、以下はこのファイルがマークダウンであるから便宜上リストで示すが、基本的にフォーマットはテーブルとして利用し、ExcelないしCSVとして流用可能なものとする。

## テスト仕様書フォーマット

- テストケースナンバー（列名:CaseNo）
- 大分類
- 中分類
- 小分類
- 観点ID
- ケース内容
- 操作手順
- 確認内容
- 確認手順
- 想定結果
- 想定結果判断基準・判断手順
- テスト実施記録(個人開発ならば不要としても可)
- 予定日
- 実施日
- 実施者
- 実施結果
- テスト再実施(個人開発ならば不要としても可)
- 再実施要否
- 再実施判断日
- 再実施判断担当者
- 再実施テスト仕様書ファイル名ないしファイルパス
- 備考

## テスト仕様書フォーマット解説

- テストケースナンバー
    - 8,16,24,32といったいずれかの桁で構成する数字とIDを紐付けたもの。IPアドレスと考え方は同じなのでこの桁にしておく
    - 個人開発ならばIDだけは全個人開発で統一定義できているとよい
    - IDはシステム名に加えて機能IDやAPIと紐付けられるようにしておくとよい
    - テスト工程やテスト観点でIDを振る必要はこのフォーマットであれば不要。なぜならケースナンバー自体がテスト工程やテスト観点を含んだ識別子になるからだ。
    - 数字は1桁毎に意味を持たせる(以下は例)
    - 1桁目から2桁までは、大分類と中分類、小分類を識別するもの
    - 3桁目から4桁目までは観点と正常/異常系、対象画面などテスト仕様書を識別するためのもの
    - 5,6,7,8桁目ではテスト仕様書内のテストケースを識別するためのものかつ、8桁目は予約済みとしておき、再テストや追加テスト、追加手順などを記載するようにしておくなど
    - 正直ちゃんとしたWebアプリでは8桁だと限界がすぐに来るため、16桁以上を採用し予約済み桁をそれぞれの区分に設けておけば運用上困らない。
    - ゆえに基本的には32桁を毎回Excelに記載しておくのは辛いので、大きく取って24としておき、いくつかの桁は予約済みとして非表示列で隠しておけばいいんではないかと考えている。
    - なお、予約済み列は｢予約済み｣とすると分からないので、予約済み=0としておけばCONCAT関数のような関数で結合しても識別しやすい。
    - 構成としては
        - SYSTEMID-12-34-56-78-910のようにしておけばよいし、ハイフンの区切りは自由に定義すればよい
        - システムIDはアプリホスト名のようにしておくと楽だと経験上感じる
- 大分類
    - 単体画面や結合APIといった粒度を記載する
- 中分類
    - 使うシーンやプロジェクトによって変えられるため、任意で良いと思うので、特段ここでは明記しない
    - 今後、サンプルは書いても良いかと考えている
- 小分類
    - 使うシーンやプロジェクトによって変えられるため、任意で良いと思うので、特段ここでは明記しない
    - 今後、サンプルは書いても良いかと考えている
- 観点ID
    - 鏡の原理とリンクさせたものとしたい
    - 記述内容や方法は考察途中
- ケース内容
    - テストする内容を書く箇所としたい
    - 記述内容や方法は考察途中
- 操作手順
    - 人がやるプロジェクトなら人の手順であり、プログラムを実行するだけなら、コマンドないしスクリプトファイル名を書くだけでよいかと思っている
    - 人がやる場合の記述内容や方法は考察途中
- 確認内容
    - テストの結果を確認するため、ログファイルやテストレポートのどんなところを確認するかを明記する箇所
    - 具体的な記述内容や方法は考察途中
- 確認手順
    - 確認内容を実施する上での操作手順を明記する
    - 具体的な記述内容や方法は考察途中
- 想定結果
    - テストコードや手打鍵でのテストによる、想定する結果を記載する。
    - テストコードならば、アサーションの内容と結果であり、手打鍵なら挙動を記載する
    - 具体的な記述内容や方法は考察途中
- 想定結果判断基準・判断手順
    - 想定結果として、例えばログファイルが出力されているものの、テスト実行時間帯に対象ログが出力されていない場合などが考えられる。この場合ログファイル出力機能であれば問題ないが、ログ出力であれば問題があるため、判断として再実行した上でログが出力されていなければエラーとする、といったことを明記する箇所
    - 具体的な記述内容や方法は考察途中
- テスト実施記録(以降は個人開発ならば不要でも良い)
- 予定日
- 実施日
- 実施者
- 実施結果
- テスト再実施
- 再実施要否
- 再実施判断日
- 再実施判断担当者
- 再実施テスト仕様書ファイル名ないしファイルパス
- 備考（ここは個人開発でも加えておく）
